Priya's PR

An agent-authored PR adds a nightly job that writes to the positions table directly — bypassing the adapter that emits the audit events. The code is clean, the tests pass, a reviewer new to the team approves it. A two-year-old ADR forbade exactly this; its author had left; nobody current remembered. The ADR was in the repository. It was never surfaced. This example records that decision as data — scope, enforcement, posture, reason — and lets the guardrail, not anyone's memory, catch the PR: once at design, once at merge, with no model on the verdict path.1

1That is the point of spec-driven development, and of spectastic in particular: a decision is an artifact — written once, in the design that made it, with a stable id — and everything downstream references it rather than re-deriving it. Remembering is a human skill; referencing is a tool's. ADR-0007 isn't a memo in a wiki; it is 002-downstream-consumers/D-007, addressable by coordinate from the spec, the plan, the verdict, and the reviewer.

Why it's a governance problem, not a review problem

The scenario is Theo Valmis's, from Architectural Guardrails for AI-Generated Code. He names the failure architectural drift — code that individually looks fine but collectively pulls the codebase away from where the team agreed it should go — and makes two claims that bite. First, an instruction file like CLAUDE.md is the right instinct at the wrong resolution: free text with no precedence, no lifecycle, no enforcement. Second, a second model reviewing the PR cannot fix this, because it shares the first model's blind spot — “two probabilistic passes over the same blind spot are not one deterministic pass with sight.” What's needed is a decision that is retrievable by path, injected before writing, and enforced by a script — not an agent, not retrieval-as-verdict, not AI-reviews-AI. spectastic's own principle P-8 says the same thing: guarantees live in the kernel or CI.

The distance

A securities position keeper — seven features, scaffolded by spectastic init --profile standard and driven through the whole lifecycle — spec → design → tasks → implement → verify — onto a real two-service Gradle build. The decision that matters was born in feature 2 as the answer to a requirement, not as governance ceremony: what guarantees every position change emits an event? Then five features and two and a half years go by without anyone mentioning it.

05 Feb 2024 · 001-position-core
Ports-and-adapters; a JDK-only domain. Positions are idempotent on tradeId.
11 Mar 2024 · 002-downstream-consumers
ADR-0007 is written. Risk and P&L need a PositionChanged event on every move, so FR-004 requires a single emitter — and the design records D-007: only the persistence adapter touches the data store. An ArchUnit fitness function ships with it; a DB grant (D-008) is the operational backstop.
20 May 2024 · 003-jdbc-persistence
Real SQL arrives. ADR-0007 is amended with a Semgrep content rule for the case a type-graph rule can't see.
Three merges that never mention it — 004-query-endpoint (Aug 2024) · 005-instrument-refdata (Nov 2024) · 006-health-check (Feb 2025). The author moves on.
13 Sep 2026 · 007-reconciliation
“Add a nightly job that corrects positions from the custodian file.” The naive implementation writes corrected quantities straight into positions — fast, clean, and exactly what ADR-0007 forbids. This is the request that tests whether the guardrail still holds.

The 2024–25 dates are narrated (docs/timeline.md); the build-out is real git history — every bundle, the Gradle build, the CI gate and every command output are committed.

The decision — recorded as data

A Nygard card with prose Context / Decision / Consequences is a decision log. What makes it a governance record is the structured half: a scope a tool can retrieve by, a posture that says block or warn, enforcement rule-ids that join a detector's finding back to the decision, and a reason that lives once — here — and is never re-typed into the enforcer's own message channel, where it would drift. And, since the amendment below, a resource: the store the decision governs, by coordinate, and the one project that owns it.

Killed twice

The layer is six stages — author → register → retrieve → inject → gate → teach — and the PR dies at two independent points. Both are deterministic. The second one also tells the author exactly why, and where to go instead.

1

Retrieval surfaces the decision — by path, to a log

Before writing, the agent (or the human) asks which decisions govern the paths about to change. The answer is a glob match over every active decision's scope — no embeddings, no ranking, the same paths always return the same decisions — and it writes a retrieval log so the plan's view can be diffed against the merge's.

$ spectastic adrs --for src/main/java/xyz/briancorbin/pk/hex/persistence/CustodianSnapshotReader.java
002-downstream-consumers/D-007  [block]  archunit:only_the_persistence_adapter_touches_data_access_apis, semgrep:no_sql_write_to_positions_outside_adapter
  governs: src/main/java/xyz/briancorbin/pk/hex/persistence/CustodianSnapshotReader.java
Wrote .spectastic/adr-retrieval.json

The same block — id, coordinate, reason — is injected into the design and tasks prompts, fenced as data to account for, never an instruction the tool obeys. It's an aid: an advisory prompt cannot be a guarantee, so nothing downstream assumes it was read.

2

Death at design — the plan constraint

A draft design's project-structure tree is its declared surface. If that surface touches a path governed by an accepted decision from another spec, the design must acknowledge it — by coordinate — or spectastic validate fails at the standard profile and up. spectastic has no diff at design time, only prose; this is a nudge where the PR should die in the happy path, and it binds forward-only (a new decision never retroactively fails the ninety-seven designs that shipped before it).

3

Death at merge — the verdict

Skip spec and design entirely; commit PositionReconciliationJob straight to a branch. The merge gate judges the actual diff against the decisions governing it and composes a verdict — {decision, rule, reason, file:line, source → target, cause} — persisted as plain JSON that reconstructs from the changed file and the decision record. Exit 1. The verdict kernel's transitive imports carry zero child-process modules: running a foreign command is not something it can do.

Both are output-only: the exit code and the artifact are byte-identical with or without them.

The residual — detector and explainer, split

spectastic is a Node CLI. It does not reimplement ArchUnit or Semgrep, and it never executes them. For language-agnostic rules — a path boundary, a forbidden pattern — it runs its own deterministic content detector. For a type-graph rule it ingests the ecosystem enforcer's SARIF and joins the rule-id back to the decision. Either way spectastic owns the one thing no architecture-test tool provides: the composition rule-id ↔ decision-id ↔ reason ↔ location.

Ownership, not layering

Split the estate into services and the sharper version of Priya's PR appears: the reconciliation team builds the nightly job in their service, and writes the position store from a persistence adapter of their own — cleanly layered, ports-and-adapters by the book. A path glob has no grammar for this. src/**/persistence/** is satisfied; the write is still wrong, because of whose store it is.

So D-007 was amended to name the store it governs by coordinate and the one project that owns it. The verdict becomes owner-aware: the current project identity is resolved once at the CLI edge from spectastic.json and injected into the pure kernel as data. If it equals the owner, the path rule applies exactly as before — demos 1–7 reproduce byte-identically. If it is anything else — another project, no identity at all, a bare unqualified default — the allowed zone is empty, and every detected touch flags.

The rubric, scored twice

Before building the layer, spectastic scored itself against Valmis's rubric under a harsh bar — a row is full only against a committed passing test — and came out 2 full · 5 partial · 3 does-not. The Priya PR would have passed. After seven specs and this example: 9 full · 1 partial · 0, with the one partial kept on purpose.

Building the layer also taught two things the rubric doesn't name: a governance layer needs forward-only binding — a new decision binds work in flight, not history — and “a failure teaches” has two halves, the data and the rendering; full data behind a one-line render reads as done and is not.

What it can't see

A guardrail that overstates its reach is a guardrail nobody should trust. Three boundaries, recorded in the tool rather than in the marketing.

The verdict reads one checkout, and says so

A decision can now name a store in another service and its owner — but the verdict still reads only this checkout's specs/*/design.html. The consumer in demo 8 works because D-007 is copied into it; the federated read that would deliver the owner's decision into a consumer's CI is deferred to spectastic-mcp. And a "touch" is still whatever the content pattern matches: an API call, a topic subscription, a migration is not a SQL string. So a green verdict carries "scope": "repo-local" and the count of decisions it evaluated — a repo-local green, reconstructable as exactly that, never misread as an estate-wide guarantee.

Wrong service is a placement question, not an enforcement one

Database-per-service saves you from the wrong thing. A resource-scoped decision (and a per-service grant) stops Priya reaching into the position store; nothing stops her rebuilding its responsibility inside the repo her team knows — a parallel store that never touches the named one. That's a boundary duplication, not a bypass — Conway's Law operating as designed — and it is invisible to every mechanical check for a correct reason. spectastic keeps it where the industry does: a design-time, human-confirmed suggestion, never a merge gate.

Injection is an aid; the gate is the guarantee

The governing decisions are injected before writing — but a prompt is a channel the model may ignore, and spectastic has watched a weaker model ignore one. Injection improves the odds the gate stays quiet. The gate fires regardless, and a test proves its answer is the same whether or not the block was injected.

Also honest: the Java is now a real two-service Gradle build — 38 tests, green on main, red on the bypass branch — but the point is still not that a project compiles. It is that a decision recorded as data, two and a half years before a request that tests it, is surfaced and enforced deterministically; what remains narrated is only the calendar.
