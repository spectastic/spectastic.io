Design · 003-jdbc-persistence

JDBC persistence

How we will build it — the second sighting of ADR-0007, and a routine one.

Status Accepted Spec 003-jdbc-persistence Owner Position Keeping team Branch build-out Created 18 Sep 2026 Read time

Implement the port with the existing JdbcPositionRepositoryAdapter over an embedded, file-backed H2 database reached through plain JDBC — no ORM, no pool. H2Database.open(path) applies db/schema.sql and db/grants.sql as the admin and hands the adapter a connection as the pk_adapter role, so D-008's grant is live at runtime, not only in a test. The write stays a literal UPDATE positions (falling back to an INSERT when no row exists) inside one transaction with the applied-tradeId row; the event is emitted on the same call, after commit. Biggest risk: the adapter is the file every guardrail demonstration points at, so its shape changes only additively.

Honoured by construction: the only class that imports java.sql is in the adapter package, its UPDATE positions is the statement the Semgrep rule's allowed-in permits, and it emits on every write. spectastic adrs --for src/main/java/xyz/briancorbin/pk/hex/persistence/JdbcPositionRepositoryAdapter.java returns D-007.
  • 002-downstream-consumers/D-008 (the DB-grant backstop, scope db/**). This plan does not change the grant files; it makes them run — H2Database.open applies them, and the adapter connects as the granted role.

3 · Data model & contracts

The spec's positions table lands as db/schema.sql declares it (002 T-012): positions(instrument VARCHAR(32) PK, quantity BIGINT) plus applied_trades(trade_id VARCHAR(64) PK, instrument), the idempotency record 001's port already implies (wasApplied).

6 · Approach

H2Database.open(Path file) connects as sa, runs db/schema.sql then db/grants.sql (both idempotent), and returns a small handle that opens connections as pk_adapter (for the adapter) or pk_reader (for 004's queries). JdbcPositionRepositoryAdapter(H2Database, EventBus) implements the port: find and wasApplied are single SELECTs; write opens a transaction, runs the existing UPDATE positions, inserts the row when the update touched none, inserts the applied_trades row, commits, and only then emits PositionChanged — on the same call, so a failed commit emits nothing and a committed write always does.

H2's MERGE INTO would do the upsert in one statement. It is not used, because the guardrail's Semgrep rule and demonstration 4a both name the literal UPDATE positions; a clever statement here would quietly change what the example proves.

8 · Decisions

D-001 · Embedded, file-backed H2 over plain JDBC

Status
Accepted
Context
The spec needs durability across a restart and D-008 needs a database with roles and grants; the example must run with no daemon. Spike (§5): reopen, idempotent DDL and role grants all hold on h2@2.3.232.
Decision drivers
no external process · GRANT support · one dependency
Considered options
  • H2, file-backed — chosen — + embedded, real users and grants, one jar. − Not what production would run; fine for a worked example.
  • SQLite — + embedded. − no users, so D-008 could not be real.
  • PostgreSQL (Testcontainers) — + production-shaped. − Docker in every build and CI job.
Decision
jdbc:h2:file:<path>; com.h2database:h2:2.3.232 as implementation; no pool, no ORM.
Consequences
+ ./gradlew run (004) needs nothing installed. + The grant is real at runtime. − H2-specific SQL state codes in the test.

D-002 · Write = UPDATE, INSERT when no row, applied-trade row, commit, then emit — one call

Status
Accepted
Context
The existing adapter's statement (JdbcPositionRepositoryAdapter.java:22) is the one the Semgrep rule and demonstration 4a name; 002 NFR-001 wants a committed position and its event never to diverge; 001/D-005 wants the tradeId recorded with the quantity.
Decision
setAutoCommit(false); UPDATE positions …; if 0 rows, INSERT INTO positions; INSERT INTO applied_trades; commit; bus.emit(…). A failure before commit rolls back and emits nothing.
Consequences
+ The literal UPDATE positions survives, so the guardrail's proofs are unchanged. + Emission after commit means no event for a rolled-back write; on the same thread means no gap in which a consumer sees the old book. − Two statements where MERGE would be one.

D-003 · The adapter connects as pk_adapter; the opener applies DDL and grants as sa

Status
Accepted
Context
D-008 is recorded as a none-with-reason because no static check can see a grant; the next best thing is for the running system to actually use the granted role, so the backstop is exercised on every write. GrantBackstopTest (002) already proves the refusal.
Decision
H2Database.open(path) runs db/schema.sql and db/grants.sql as sa, then exposes adapterConnection() (pk_adapter) and readerConnection() (pk_reader). Passwords are the role names — an embedded file with no listener; recorded as the P-9 exception.
Consequences
+ Least privilege is real: a second writer connecting as anything but pk_adapter is refused by the database. − Two connections per process instead of one.

11 · Complexity tracking

Two roles and an opener are more than a demo needs; they exist so D-008 is a live grant rather than a comment, which is the point of this feature's second sighting of ADR-0007.

The applied-tradeId record lives in the database (not the use case), because the port already asks the adapter wasApplied — 001/D-005 — and durability must cover it too or a restart would double-count.
