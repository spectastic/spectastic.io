Design · 004-query-endpoint

Position query endpoint

How we will build it — the first entry point, and a feature that never mentions the decision.

Status Accepted Spec 004-query-endpoint Owner Position Keeping team Branch main Created 18 Sep 2026 Read time

A GET /positions/{instrument} served by the JDK's own com.sun.net.httpserver — no web framework — reading through PositionService.current and so through the persistence adapter. The contract is an OpenAPI sidecar authored first (P-7). Main arrives here: it opens the H2 file, wires the bus, the adapter, the two consumers and the HTTP server. Biggest risk: a read path that accidentally writes — the test asserts zero events and an unchanged store across every request.

3 · Data model & contracts

The spec's Position view is the wire shape {"instrument": "AAPL", "quantity": 100} — 001's Position record, serialised. Nothing is stored; the projection is computed per request from PositionService.current.

Conceptual entityPhysical shapeNotes
Position viewapplication/json object {instrument: string, quantity: int64}404 {"error": "unknown instrument"} when nothing was ever booked; 405 for any method but GET.

One resource, one verb. A consumer may rely on: a known instrument returns 200 with the current signed quantity as a JSON integer; an unknown one returns 404 with an error string, never an empty body; and no request on this surface — whatever the method — changes a position. The contract is authored at the proposed location (specs/004-query-endpoint/contracts/) while the design is in flight and promoted to api/ when the bundle lands.

6 · Approach

hex.http.HttpApi wraps an HttpServer: start(), stop(), port(), and a context per handler. PositionsHandler takes the instrument from the path, refuses anything but GET with 405, asks PositionService.lookup, and writes 200 {instrument, quantity} or 404 {error} through a ten-line Json helper. Main reads PK_PORT (default 8080) and PK_DB (default data/pk), opens H2Database, builds a SyncEventBus, the JDBC adapter, the RiskExposureView and PnlRevaluer, the PositionService, and starts the API. It imports no java.sql.

The temptation is a framework — Javalin, Helidon — for the routing and JSON. Two routes and one object do not earn a dependency tree, and the example's supply-chain principle (P-12) is easier to keep than to restore.

8 · Decisions

D-001 · The JDK's HTTP server, no web framework

Status
Accepted
Context
Two routes (this and 006's health) and one JSON object. 001's spike compiled HttpServer on the toolchain with no dependency; P-12 asks that adding one be a reviewed decision — this is the review.
Decision drivers
zero dependencies · code volume · the JDK-only story
Considered options
  • JDK com.sun.net.httpserver — chosen — + nothing to add; ephemeral ports for tests. − Hand-rolled routing and JSON.
  • Javalin — + pleasant API. − Jetty and Jackson for two routes.
  • Spring Boot — + conventional. − a framework the rest of the example deliberately lacks.
Decision
HttpServer behind hex.http.HttpApi; a Json helper for the two object shapes; Gradle application plugin for ./gradlew run.
Consequences
+ ./gradlew run starts with one jar on the classpath (H2). − Anything beyond a handful of routes would want a framework; that is a later decision if it comes.

D-002 · Contract first: an OpenAPI 3.1 sidecar, promoted to api/ when the bundle lands

Status
Accepted
Context
P-7 requires a checked-in contract before the code behind an interface, and the validator will not accept a request/response declaration without a path (contract-declaration-shape.ts:80). The interview seeds OpenAPI for request/response.
Decision
specs/004-query-endpoint/contracts/positions.openapi.yaml now; declared effective path api/positions.openapi.yaml, coordinate name positions; moved to the effective path on the bundle's last tick. The handler is written to it, not the other way round.
Consequences
+ A consumer (the reconciliation service, 010) has a target before the code exists. − Two copies exist for a moment at promotion; the move is a single git mv.

D-003 · Read-only by construction: GET-only routing over PositionService.lookup

Status
Accepted
Context
Spec FR-002 forbids mutation; NFR-001 wants the existing adapter. PositionService.current exists; it flattens an unknown instrument to zero, so the handler needs an Optional-returning lookup to answer 404.
Decision
Add Optional<Position> lookup(String) to the use case (delegating to find); the handler holds only the service; non-GET → 405 before any lookup.
Consequences
+ The handler cannot write: it has nothing to write with. + The test observes “no write” as zero events and an unchanged store. − One more method on the use case.

11 · Complexity tracking

Hand-written routing and JSON are the only complexity beyond the spec, and they replace a dependency tree; justified in D-001.

The store's contents are read as the adapter's role (pk_adapter), because NFR-001 asks for the existing adapter and 003's adapter owns that connection. The reader role is for probes that bypass the port (006).
