1 · Context

A position keeper turns a stream of trade events into current positions. It must be idempotent (a redelivered trade cannot double-count) and keep the domain free of infrastructure so persistence can change later. This is the base every other feature builds on.

2 · User scenarios & testing

A trade updates a position. Booking a buy of 100 sets the position to 100.

Idempotent on tradeId. Re-booking the same tradeId leaves the position at 100.

3 · Requirements

Applying a trade event MUST update the instrument’s position by the trade quantity. Applying a trade event whose tradeId was already applied MUST NOT change the position (idempotent). The domain MUST be reachable only through ports; the repository is an adapter behind a port. The domain MUST depend on the JDK only — no framework, no persistence library imported into the core.
  • Emitting events to consumers — the next feature.
  • Durable persistence — in-memory here; JDBC later.

4 · Data model

Position
an instrument and a signed quantity; the running sum of applied trades.
Trade event
an instrument, a signed quantity, and a unique tradeId (the idempotency key).

5 · Success criteria

Booking a trade updates the position, and re-booking the same tradeId leaves it unchanged.
Observed at

A unit test applying a trade, then the same trade again.

 The domain compiles with no import of any framework or persistence library.
