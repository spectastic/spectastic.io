Design · 001-position-core

Position keeping core

How we will build it — and the Gradle build every later feature compiles into.

Status Accepted Spec 001-position-core Owner Position Keeping team Branch build-out Created 18 Sep 2026 Read time

A JDK-only hexagonal core — Position and TradeEvent records, a PositionRepository port, a PositionService use case that decides idempotency against the repository's applied-tradeId record — plus the Gradle 9 build (Groovy DSL, Java 21 toolchain, JUnit 5, ArchUnit, Spotless, Checkstyle) that this and the six later features compile into. The single biggest risk is the build itself: it is the first real one in this repository, and spectastic enforce only recognises a Gradle build written in the Groovy DSL.

Toolchain / enforcement

The three gaps resolve on the first rung of the escalation ladder — the ecosystem's standard gates, all in build.gradle so detection sees them: Spotless 8.10.2 running google-java-format 1.36.1 (formatter), Checkstyle 14.1.0 with a minimal config/checkstyle/checkstyle.xml (linter), and Gradle's test task on the JUnit Platform (test-runner). The CI gate for all three is the spectastic-managed workflow spectastic init --tools --ci github writes (validate → enforce → merge verdict on every pull request); a second, project-owned workflow runs ./gradlew build. spectastic gitignore --stack ran before the build existed and detected no stack; it re-runs in the setup phase once build.gradle is present, and .gradle/ is added by hand outside the managed block because the Java entry set (build/ target/ *.class) does not include it.

3 · Data model & contracts

The spec's two entities land as Java records in the core package: Position is (String instrument, long quantity); Trade event is (String tradeId, String instrument, long quantity). Quantity is a signed long — whole units, no fractional lots in this timeline. The applied-tradeId record is the repository's, not the entity's: the port answers wasApplied(tradeId), and write records the tradeId together with the new quantity so the two can never disagree.

Conceptual entityPhysical shapeNotes
Positionrecord Position(String instrument, long quantity)Immutable; the repository returns a fresh value per read.
Trade eventrecord TradeEvent(String tradeId, String instrument, long quantity)tradeId is the idempotency key (FR-002).
Repository portinterface PositionRepository { Optional<Position> find(String); boolean wasApplied(String); void write(String instrument, long quantity, String tradeId); }write keeps the signature the existing adapter already implements.

No interface is exposed: the core is a library reached through its ports (FR-003). The HTTP surface is 004's and the event stream 002's; each declares its own contract there.

6 · Approach

Bootstrap the build first — settings.gradle, build.gradle, the wrapper, Spotless and Checkstyle — because nothing else in this repository has ever compiled and every later feature needs the same four files. Then the core: xyz.briancorbin.pk.hex.core holds the two records and the PositionRepository port; xyz.briancorbin.pk.hex.app.PositionService is the one use case, book(TradeEvent): ask the repository whether the tradeId was applied, return the current position unchanged if so, otherwise add the quantity and write the new quantity and the tradeId together. xyz.briancorbin.pk.hex.persistence.InMemoryPositionRepository is the first adapter — a map and a set. The existing JDBC adapter moves into the Gradle layout as-is; making it compile against H2 is 003's work.

Idempotency could have lived in the adapter (“ignore a write whose tradeId you have seen”). It lives in the use case instead so that FR-002 holds for every adapter, including the JDBC one that 003 writes and the reconciliation path 007 adds.

8 · Decisions

D-001 · Gradle 9 with the Groovy DSL and a Java 21 toolchain

Status
Accepted
Context
The project has never had a build. spectastic enforce reads Java signals from build.gradle only (detect.ts:118-170), and the spike showed Gradle's toolchain resolver finds the asdf Temurin 21 on the JDK 25 host with no configuration.
Decision drivers
enforce detection · zero-config JDK 21 · least build code
Considered options
  • Gradle 9, Groovy DSL — chosen — + every gate visible to enforce; toolchain provisions 21. − Groovy is the less type-safe DSL.
  • Gradle 9, Kotlin DSL — + type-safe. − enforce would report the floor as uncovered forever.
  • Maven — + ubiquitous. − no toolchain provisioning; formatter/linter invisible to enforce.
Decision
settings.gradle + build.gradle (Groovy), Gradle 9.2.1 wrapper committed, java.toolchain.languageVersion = 21.
Consequences
+ One build for all seven features and, later, the consumer subproject. + ./gradlew works on any JDK 17+ host. − Groovy DSL; − the wrapper jar is a committed binary.

D-002 · Hexagonal ports-and-adapters

Status
Accepted
Context
FR-003 requires the domain be reachable only through ports, and the existing adapter already implements PositionRepository.write (JdbcPositionRepositoryAdapter.java:16). 002's D-007 depends on this shape: the adapter package is the boundary its rule names.
Decision drivers
FR-003 · the boundary D-007 enforces · simplest structure that isolates the store
Considered options
  • Hexagonal ports-and-adapters — chosen — + the store is behind one port; the adapter package is a checkable boundary. − One more interface than a layered service needs.
  • Layered (service → repository class) — + familiar. − the repository is a class, not a port; nothing stops a second writer.
  • Vertical slice — + feature-local. − seven features would each own a slice of the same store.
Decision
Packages hex.core (records + ports, JDK-only), hex.app (use cases), hex.persistence (adapters). Dependencies point inward; ArchUnit asserts it.
Consequences
+ Swapping in-memory for JDBC (003) touches only hex.persistence. + D-007's scope is a real package. − Ceremony for a small domain.

D-003 · JUnit 5 + ArchUnit, test-first

Status
Accepted
Context
SC-002 is observed by an ArchUnit rule, and D-007's fitness function is already written against ArchUnit (enforcement/DataAccessRulesTest.java). The spike resolved junit-bom:5.11.4 and archunit:1.4.1 and ran both.
Decision drivers
SC-002's stated observation · reuse of the existing rule · the standard profile's test-runner floor
Considered options
  • JUnit 5 + ArchUnit, TDD — chosen — + the JUnit Platform is what Gradle's test runs; ArchUnit is the only mainstream Java architecture checker. − ArchUnit has no SARIF output of its own.
  • JUnit 4 — − ArchUnit's JUnit 4 support is legacy; no reason to prefer it.
  • Integration-first — − there is nothing to integrate against until 003/004.
Decision
Tests under src/test/java, written before the code they exercise; ArchUnit rules are plain @Test methods that evaluate a rule (so later a SARIF writer can sit beside the assertion).
Consequences
+ SC-001/SC-002 each have a test that fails before its implementation task. − Plain @Test forgoes ArchUnit's @ArchTest field syntax.

D-004 · Enforcement floor: Spotless + Checkstyle + Gradle test, gated by the managed CI workflow

Status
Accepted
Context
spectastic enforce lists formatter, linter and test-runner missing (this turn). All three are first-rung ecosystem gates; versions from the plugin-portal and Maven Central metadata read this turn.
Decision
Spotless 8.10.2 (google-java-format 1.36.1) · Checkstyle 14.1.0 with a minimal config · test { useJUnitPlatform() }. CI: spectastic init --tools --ci github installs the managed .github/workflows/spectastic.yml (validate → enforce → verdict); a project-owned build.yml runs ./gradlew build.
Consequences
+ enforce reports the floor covered; ./gradlew build fails on an unformatted or lint-failing file. + The CI gate is a file spectastic owns and drift-checks, pinned to the installing CLI. − Two workflows rather than one, because the managed file is not to be edited.

D-005 · Idempotency is decided in the use case against the repository's applied-tradeId record

Status
Accepted
Context
FR-002 must hold for every adapter. The existing adapter's write(instrument, quantity, tradeId) already receives the tradeId (JdbcPositionRepositoryAdapter.java:20), so recording it beside the quantity costs the port nothing.
Decision
PositionService.book checks wasApplied(tradeId) before computing; write stores quantity and tradeId together (one map put + one set add here; one transaction in 003).
Consequences
+ One idempotency rule, adapter-independent. + 007's reconciliation tradeIds reuse it. − The port grows by two read methods.
