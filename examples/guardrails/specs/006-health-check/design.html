Design · 006-health-check

Health check

How we will build it — a probe port, a read-only role, and a second route on the server 004 built.

Status Accepted Spec 006-health-check Owner Position Keeping team Branch build-out Created 18 Sep 2026 Read time

A StoreProbe port in the core (boolean reachable()), an H2StoreProbe adapter that runs SELECT 1 as the read-only pk_reader role, and a HealthHandler on GET /health answering 200 {"live":true,"ready":true} or 503 {"live":true,"ready":false}. The contract is a second OpenAPI sidecar. Biggest risk: a probe that can write; it cannot — the role has no write grant and the port has no write method.

3 · Data model & contracts

The spec's Health status is {"live": bool, "ready": bool}: live is true whenever the handler answers at all; ready is the probe's answer. The status code carries the same fact: 200 when ready, 503 when not.

Conceptual entityPhysical shapeNotes
Health statusapplication/json {live: boolean, ready: boolean}200 / 503; 405 for any method but GET.
Store probe (port)interface StoreProbe { boolean reachable(); }JDK-only, in hex.core; the H2 adapter is the only implementation outside tests.

A consumer (the orchestrator) may rely on: 200 means the store answered a query in this request; 503 means the process is up but the store did not; the body always carries both booleans. Authored at the proposed location and promoted to api/ when the bundle lands, as 004's was.

6 · Approach

Add StoreProbe to hex.core. H2StoreProbe(H2Database) opens a reader connection and runs SELECT 1; any exception is false. HealthHandler(StoreProbe) answers GET with the JSON pair and the matching status, 405 otherwise. Main registers /health beside /positions/.

Liveness could also check the bus or the consumers, but they are in-process objects with nothing to fail; a liveness that is always true is the honest one here.

8 · Decisions

D-001 · Readiness is a StoreProbe port answered by SELECT 1 as the reader role

Status
Accepted
Context
Spec FR-002 needs the store's reachability; NFR-001 forbids mutation. H2Database.readerConnection() and the grant (§5) make a probe that cannot write.
Decision drivers
cannot mutate · port discipline · one query
Considered options
  • Port + SELECT 1 as pk_reader — chosen — + read-only by grant. − one more port.
  • Reuse find — − runs as the adapter's writable role; misuses the port.
  • File exists — − says nothing about the database answering.
Decision
interface StoreProbe { boolean reachable(); } in hex.core; H2StoreProbe in hex.persistence.
Consequences
+ Tests toggle readiness with a lambda. − The persistence package grows by one read-only class (acknowledged above).

D-002 · Contract first: a second OpenAPI sidecar, coordinate health

Status
Accepted
Context
Same reasoning as 004/D-002; a second contract needs its own coordinate name (contract-name-unique).
Decision
specs/006-health-check/contracts/health.openapi.yaml → api/health.openapi.yaml at the last tick; name="health".
Consequences
+ The orchestrator's contract is a file. − Two small OpenAPI documents rather than one; merging them is a later editorial choice.
