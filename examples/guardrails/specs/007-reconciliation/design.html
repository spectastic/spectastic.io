3 · Data model & contracts

The job consumes the custodian file (instrument, quantity) and emits corrections as ordinary use-case calls carrying a reconciliation tradeId. Since change 2026-09-18-http-corrections the same correction path is also reachable over HTTP, for a downstream service that computes its own deltas — the contract below.

POST /corrections with {instrument, quantity, tradeId} brings the instrument to quantity through PositionService.correct — the same path the nightly job uses — and answers the resulting position. A caller may rely on: a repeated tradeId is a 200 that changes nothing; every applied correction emitted PositionChanged before the response; the caller never touches the store. 6 · Approach

A scheduled job parses the custodian file, reads current quantities through a persistence-package snapshot reader (using the existing adapter, not a new writer), computes per-instrument deltas, and applies each as a use-case correction carrying the run's tradeId. Every correction therefore emits PositionChanged, and ADR-0007's boundary is untouched.

8 · Decisions

D-001 · Corrections flow through the position use case

Context. Reconciliation touches positions, governed by 002-downstream-consumers/D-007; the domain rationale is settlement-window drift (KB-0001@2026-09-13). Decision. Apply every correction through the use case (emitting the event); read the current store through the adapter; add no new writer. Consequences. + ADR-0007 holds; Risk/P&L/audit see every correction. − One event per corrected instrument (fine at end-of-day volumes).
