Nightly reconciliation

"Add a nightly job that corrects positions from the custodian file." The request that, two years and five features after ADR-0007 was written, tests whether the guardrail still holds.

1 · Context

Positions drift from the custodian's records — a corporate action booked late, a settlement fail. The custodian sends an end-of-day file; a nightly job must bring the store into line. The naive implementation writes the corrected quantities straight into the positions table, which is fast, clean, and exactly what ADR-0007 forbids: a direct write bypasses the PositionChanged emission, so Risk, P&L, and the audit trail never learn the position moved. The reconciliation must correct through the use case, emitting an event per correction.

2 · User scenarios & testing

A drifted position is corrected — audibly. The custodian file shows a quantity that differs from the store; the job computes the delta and applies it through the position use case, which emits PositionChanged. Risk and P&L see the correction.

No direct write. The job never touches the positions table directly; the correction path is the same adapter every other mutation uses.

3 · Requirements

The job MUST read the custodian end-of-day file and compute, per instrument, the delta between the custodian quantity and the stored quantity. Each correction MUST be applied through the position use case, so every corrected position emits a PositionChanged event — the job MUST NOT write the position store directly. (This is what ADR-0007 governs.) A correction MUST carry a synthetic tradeId identifying the reconciliation run, so consumers stay idempotent and the audit trail attributes the change. The job SHOULD be re-runnable for the same custodian file without double-correcting (idempotent on the run's tradeId).

The service MUST accept a correction from a downstream reconciliation service over POST /corrections — instrument, the custodian quantity that service reconciles against, and a synthetic tradeId identifying that service's reconciliation run — and apply it through the position use case, so it emits PositionChanged like every other mutation; a repeated tradeId MUST change nothing and answer the current position.

Rationale

ADR-0007's verdict on a non-owner service tells it to route the change through the owner. This is the route. It reuses the job's correction path so that there is still exactly one way a position changes.

 A reconciliation run MUST leave the store and the emitted events consistent: no position is corrected without a matching event.
  • How the custodian file arrives (SFTP, drop) — an ops concern.
  • Alerting on large drift — a later observability feature.

4 · Data model

Custodian record
An instrument and the custodian's settled end-of-day quantity — the source of truth to reconcile against.
Correction
A delta applied through the use case, carrying a reconciliation tradeId; it emits an event.

5 · Success criteria

After a reconciliation run over a file with drift, every corrected position has emitted a PositionChanged event that Risk observed, and the store matches the custodian quantities.
Observed at

An integration test running the job over a fixture custodian file and asserting one event per correction.

 Re-running the job over the same custodian file produces no second correction (idempotent on the run's tradeId).
Observed at

A test running the job twice over one file and asserting a single correction per instrument.

6 · Assumptions

  • The position use case (001) accepts an externally-supplied tradeId for attribution.
  • Reconciliation is against the custodian's settled snapshot (KB-0001@2026-09-13): the book is trade-date, the custodian is settlement-date, and the window between them is where drift lives.

7 · Open questions

None outstanding — the correction path (through the use case) is dictated by ADR-0007.
